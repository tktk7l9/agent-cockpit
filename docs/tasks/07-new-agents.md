# 07. Support for other agents (Gemini CLI / opencode / Copilot CLI)

## Background / Goal

Thanks to the lib adapter structure, adding an agent can be made routine work. This runbook gives "the general procedure for adding one agent" plus research notes on three candidates. **This machine has almost no real configuration for the target tools** (`~/.copilot` is nearly empty, `~/.gemini` and `~/.config/opencode` do not exist), so **the first step MUST be an on-the-ground investigation of the format**.

## Step 0: Format investigation (MUST NOT be skipped)

Before implementing, always confirm the following from the target CLI's official documentation (and, where possible, real files generated by installing it locally), and paste the findings into the PR description:

1. Path and format (JSON/TOML/YAML) of the user-scope config
2. Key structure of MCP server definitions (how stdio/remote are expressed, how env is held)
3. Whether concepts equivalent to skills / agents / instructions exist, and their paths
4. The project-scope mechanism
5. **Write safety**: whether the CLI keeps other state in that file (if it is a ~/.claude.json type, surgical editing is mandatory)

Research notes (participant knowledge as of 2026-07 — **do not take at face value; verify**):
- **Gemini CLI**: `~/.gemini/settings.json` (JSON; has an `mcpServers` key; `command/args/env` + `url` forms similar to Claude), instructions are `GEMINI.md`. Project: `.gemini/settings.json`
- **opencode**: `~/.config/opencode/opencode.json` (JSON, `mcp` key; the format likely differs from Claude), reads AGENTS.md
- **Copilot CLI**: `~/.copilot/mcp.json` etc. The format is in flux

## Steps 1 to n: general procedure for adding an agent (using Gemini as the example)

### 1. Types and scanning

- `src/lib/model/types.ts`: add `"gemini"` to `AgentId`. **Widening this union makes every exhaustive switch/Record in the UI fail typecheck — that becomes the TODO list** (`AGENT_LABEL`, the filter chip array `AGENTS`, add `.badge-gemini` / `.chip-gemini` colors in styles.css)
- `src/lib/paths.ts`: add a path function such as `geminiDir(home)` + add files/dirs to `scanSpec` (add a new tag to `SnapshotTag` only if needed. If existing tags (mcpJson/skill/instructions…) can express it, do not add tags — e.g. if Gemini's settings.json is the simple `{mcpServers}` form, the `mcpJson` tag + `agent: "gemini"` suffices, but if other keys live in it, use a dedicated tag)
- `watchPaths` is derived from scanSpec, so it follows automatically

### 2. Reader

- New `src/lib/agents/gemini.ts`. Use whichever is closer of the existing `cursor` (simple JSON) or `codex` (TOML, state co-located) as the template
- Add a case to `src/lib/inventory.ts`. Continue on errors with `fail(path, e)`

### 3. Writing

- If MCP is to be editable: add `{ kind: "gemini" }` to `McpSource` / `McpTargetRef` → add branches to `planUpsertMcp`/`planDeleteMcp` (for JSON, reuse the `mcpJsonPath` family; **for files with other keys co-located, only surgical jsonc editing**) → add a branch to `oldMcpSecrets` → add to McpView `targetOptions`
- instructions (GEMINI.md) can use `writeRaw` as is (just add the tag to scanSpec)

### 4. Tests

Cover every added reader and every planner branch with synthetic fixtures (the 100% gate enforces this). Add the new surface to the scanSpec test in `tests/paths.test.ts`.

### 5. UI finishing

- `components/ui.tsx` `AGENT_LABEL` / App.tsx `AGENTS` / styles.css badge and chip colors (define the CSS variable `--gemini`. Pick a brand-derived color that does not collide with the others)
- Add a column to the support table in README.md

## Verification

- Install the target CLI, create real config, and do the round trip: scan display → edit → confirm it takes effect on the CLI side (e.g. the equivalent of `gemini mcp list`) → restore from Backups
- If a real CLI cannot be prepared, **do not include it in the release** (whether to ship it as read-only display is the user's decision)
